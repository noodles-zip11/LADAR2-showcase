# M7 面试讲稿

## 1. 60 秒版本

这个项目是一个旋转式 2D LiDAR 感知系统。MCU 通过 UART DMA 接收 TF-Luna 数据，根据编码器和电机状态估算每个点的采样时间和角度，再通过两帧 CAN 报文发送给上位机。上位机按 `seq` 重组点数据，写入 CSV，并提供实时/回放的 2D 点云界面。

我做这个项目时不只是让界面显示点云，而是把链路做成可解释、可复现、可验证的工程闭环：冻结 CAN 和 CSV 契约，区分 MCU 采样时间和上位机接收时间，加入诊断和自检，跑长稳基线，并用墙面和盒子数据评估几何质量。

## 2. 3 分钟讲法

### 2.1 问题和目标

我希望做一个可复现的嵌入式感知项目，而不是一次性的演示。目标是用旋转式距离传感器扫描 2D 环境，并且可靠地把数据从 MCU 传到上位机，同时保留足够的时间和角度信息，方便回放、调试和分析。

### 2.2 MCU 链路

MCU 侧主要有三部分：

- USART2 DMA + IDLE 接收 TF-Luna 字节块。
- parser 负责找帧头、验 checksum、过滤无效数据、估算采样时间和角度，并输出点。
- CAN 把每个点拆成 `0x123` 和 `0x124` 两帧，通过 8 位 `seq` 配对。

### 2.3 上位机链路

上位机按 `seq` 重组 CAN 双帧，半帧等待超过 50 ms 就丢弃并计数；完整点会写入固定 CSV 格式，并显示为 2D 点云。回放也使用同一份 CSV 契约，所以历史采集可以继续用于调试和几何分析。

### 2.4 验证证据

我把验证证据按 milestone 放在仓库里：

- M3 记录 CAN 诊断和 ACK fault recovery 证据。
- M4 证明上位机接收、存储、回放和显示闭环。
- M5 记录短长稳基线：`6116.0 s`、`612466` 点、`0.001143%` CAN 重组丢包率。
- M6 记录几何指标：墙面直线 RMSE `7.44 mm`，盒子重复性 p95 `20.00 mm`，闭合缝隙 `11.82 mm`。
- M6.5 验证了可选 MQTT 插件在本地和 Windows 上板场景下的最小闭环。

### 2.5 边界

我刻意把云端、ESP32 和 AI 放在 V1 之外。第一阶段先保证感知链路稳定、可解释、可复现。等数据契约、回放路径和验证方法稳定后，再往标注、AI 或云端扩展会更稳。

## 3. 高频问答

### 为什么用 CAN？

CAN 是稳定的嵌入式总线，有硬件过滤、错误报告和清晰的帧级契约。对这个项目来说，总线行为和诊断计数本身就是工程价值。云端或 MQTT 可以放在上位机层扩展，不需要改变 MCU 点云协议。

### 为什么一个点要拆成两帧 CAN？

经典 CAN 每帧只有 8 字节载荷。一个点需要距离、角度、质量、采样时间、原始角度 tick 和状态字段，放不进一帧。拆成 `0x123` 和 `0x124` 后，每帧定长、解析简单，上位机按 `seq` 配对即可。

### 如果丢了一帧 CAN 怎么办？

上位机最多等待 50 ms。如果匹配帧没有到，就丢弃这个点并计入统计。协议层不伪造点、不重发、不插值，避免把通信异常伪装成真实测量。

### 为什么要区分 `t_sample_us` 和 `host_rx_time_us`？

它们回答的是两个问题。`t_sample_us` 是 MCU 侧估算的采样时间，用于点序和几何语义；`host_rx_time_us` 是上位机完成点重组的时间，适合看传输延迟和回放，不应该替代采样时间。

### 角度同步怎么做？

每个 UART chunk 到达时，固件会记录微秒时间和编码器快照。对 chunk 内每个 LiDAR 帧，固件估算帧中心时间，再根据电机速度回推编码器 tick，折回单圈后得到 `angle_tick` 和 `angle_deg`。

### 怎么证明稳定性？

M5 基线运行了 `6116.0 s`，重组了 `612466` 个点。上位机 summary 记录了重组 timeout/drop、刷新率和转速波动。它是可用基线，但我不会把它说成严格 4h 通过。

### 最大的误差来源是什么？

包括机械安装、传感器近场行为、目标摆放、边缘反射、电机速度波动和显示连线策略。M6 结果显示墙面直线明显比盒子更干净，说明核心距离-角度配对基本可用，剩余几何问题应优先从机械、分析和显示层排查，再考虑改固件同步。

### 下一步会改什么？

第一，补严格 4h 或 8h 长稳，并同时记录温升和诊断 UART。第二，继续做机械校准和墙面/盒子几何测试。第三，在 CSV 回放链路之上做 M8 标注闭环。云端、AI 和 ESP32 应该放在这之后，因为它们依赖稳定数据和标签。

## 4. 不要这么说

- 不要说严格 4h 长稳已经通过，除非重新跑并归档。
- 不要说完整 Bus-Off 注入已经验证；当前证据是 ACK fault recovery，Bus-Off 是后续更强测试。
- 不要把 MQTT 说成 V1 主价值。它只是可选的本地/plugin 扩展。
- 不要说硬件外壳或量产级已经完成。
