# 架构设计与范围边界

## 1. 架构设计

### 1.1 设计目标

本阶段目标是在现有 `Linux` 端代码基础上完成重构。

本阶段重构必须遵守以下边界：

- 不修改任何 `MCU` 代码。
- 严格遵循 `MCU` 当前发送逻辑。
- 不破坏现有 `Linux` 端已经实现的功能。
- 在现有功能基础上，为后续增加 `MQTT` 网关、远程命令和平台对接能力预留结构。
- 后续会增加 `ESP32`，因此新设计应尽量便于迁移到 `ESP32`。

> 注意：本阶段不加 `ESP32`。

### 1.2 当前主链路定位

当前系统的核心链路为：

```text
LiDAR 采样
-> MCU 距离/角度配对
-> CAN 发送
-> Linux 接收解析
-> 点云显示 / CSV 存储 / 历史回放
```

本项目当前阶段仍以感知链路、数据通信、`Linux` 工具链和稳定性验证为核心，不将 `MQTT`、云端平台和复杂 `IoT` 展示纳入第一阶段主线。

当前已经完成 `MCU` 到 `Linux` 的 `CAN` 通信、解析和实时点云显示，因此后续扩展重点不再是“打通通信”，而是“给 `Linux` 侧补对外消息出口”。

### 1.3 扩展设计原则

为避免后续增加 `MQTT` 或联网功能时破坏现有主链路，`Linux` 侧程序按以下层次进行分层设计：

- 输入层
- 解析层
- 核心处理层
- 输出层

各层之间仅通过明确的数据对象交互，不直接跨层耦合。

本阶段扩展遵循以下原则：

- 不修改 `MCU` 现有主链路的核心协议语义。
- 不因后续联网需求打乱当前采集、解析、显示、存储、回放主流程。
- 不将高频原始点云直接作为第一版 `MQTT` 上报主体。
- `MQTT` 仅作为 `Linux` 输出层的后续扩展插件接入。
- 扩展功能优先复用现有解析与处理结果，而不是重新复制一套数据链路。
- 所有新增模块都应可独立启停，不影响当前系统最小可运行闭环。
- 扩展项不得影响当前实时显示、`CSV` 录制、历史回放和测试验证主流程。

### 1.4 分层架构

#### 1.4.1 输入层 Input

定位：主链路，后续尽量不动。

输入层负责从不同来源接收原始数据，不关心后续显示、存储和网络发布逻辑。

当前输入来源包括：

- `CAN` 实时接收
- 串口接收，如后续需要
- `CSV` 回放源

建议模块：

- `input_can.py`
- `input_serial.py`
- `input_replay.py`

#### 1.4.2 解析层 Parser

定位：主链路，后续尽量不动。

解析层负责把输入层收到的原始帧解析成统一内部数据结构，不处理显示和网络逻辑。

主要职责包括：

- `CAN` 双帧重组
- 字段解析
- 时间戳整理
- 状态码整理
- 非法帧、丢帧、截断帧识别
- 输出统一点数据对象

建议模块：

- `protocol_parser.py`
- `point_assembler.py`

#### 1.4.3 核心处理层 Core

定位：项目核心价值层。

核心处理层负责与项目业务强相关的处理逻辑，是系统内部最核心的一层。

主要职责包括：

- 点云点构建
- 极坐标转直角坐标
- 扇区统计
- 最小距离提取
- 状态汇总
- 告警判断
- 调试统计信息生成

建议模块：

- `point_processor.py`
- `telemetry_builder.py`
- `alarm_detector.py`
- `diag_stats.py`

#### 1.4.4 输出层 Output

定位：扩展挂载点。

输出层负责将核心处理层产出的结果输出到不同目标，不反向耦合输入和解析逻辑。

当前输出目标包括：

- 实时点云显示
- `CSV` 存储
- 调试日志

后续预留输出目标包括：

- `MQTT` 发布
- 远程命令订阅
- 平台对接

建议模块：

- `output_plot.py`
- `output_csv.py`
- `output_log.py`
- `can_mqtt.py`，当前 MQTT 输出插件

### 1.5 当前数据流

当前系统数据流如下：

```text
LiDAR
-> MCU 距离/角度配对
-> CAN 发送
-> Linux 输入层
-> 解析层完成双帧重组与字段整理
-> 核心处理层完成点云构建、统计与状态判断
-> 输出层
```

输出层当前分别用于：

1. 实时点云显示
2. `CSV` 存储
3. 调试日志输出

用分层形式表示为：

```text
LiDAR
-> MCU
-> input_can
-> protocol_parser / point_assembler
-> point_processor / telemetry_builder / alarm_detector
-> output_plot
-> output_csv
-> output_log
```

该数据流体现出当前系统已经形成“采集 -> 解析 -> 处理 -> 输出”的本地闭环，后续 `MQTT` 扩展只应挂接在输出层，而不应反向侵入前面的输入、解析和核心处理主链路。

### 1.6 后续 MQTT 扩展挂载位置

后续若增加 `MQTT`，不改变输入层、解析层和核心处理层，仅在输出层新增 `MQTT` 网关模块，不入侵主链路。

扩展后的数据流为：

```text
LiDAR
-> MCU
-> CAN
-> Linux 输入与解析
-> 核心处理
-> 点云显示 / CSV 存储 / 调试日志 / MQTT 状态、摘要、告警发布
```

即 `MQTT` 作为 `Linux` 输出插件存在，而不是反向侵入主链路。

### 1.7 架构设计收益

采用上述分层架构后，系统具有以下收益：

- 主链路重点明确，项目核心仍然聚焦在感知链路、数据通信、`Linux` 工具链和稳定性验证。
- 输入、解析、处理、输出边界清楚，便于调试、回放和问题定位。
- 后续增加 `MQTT` 时，只需在输出层新增模块，不需要推翻现有主流程。
- 可以在不改动 `MCU` 主协议的前提下，为系统增加对外通信能力。
- 有利于将当前“本地采集与显示系统”逐步升级为“终端网关系统”。
- 简历表达上既能突出当前项目的工程完整性，也能体现后续可扩展能力。

## 2. MQTT 扩展目标与定位

`MQTT` 在本项目中的定位是 `Linux` 侧输出插件，而不是主链路的一部分。

第一阶段 `MQTT` 扩展目标是：

- 增加 `MQTT` 网关能力。
- 支持状态上报。
- 支持摘要遥测上报。
- 支持告警上报。
- 预留简单远程命令下发能力。
- 为后续平台对接和 `ESP32` 迁移预留结构。

本阶段不把 `MQTT` 作为高频原始点云通道，也不通过 `MQTT` 反向改变 `MCU` 主协议。

## 10. 当前阶段不做与后续扩展

### 10.1 当前阶段不做

当前阶段不做以下内容：

- `ESP32` 联网协处理器接入。
- 云端平台接入。
- 全量原始点云 `MQTT` 高频转发。
- 复杂 `Web` 前端或远程控制面板。
- 因联网而修改 `MCU` 主协议主结构。

### 10.2 后续扩展

后续扩展可以围绕以下方向展开：

- 在输出层新增 `MQTT` 发布模块。
- 在输出层新增远程命令订阅模块。
- 在不影响主链路的前提下接入平台。
- 在 `Linux` 侧插件结构稳定后，再考虑迁移或复用到 `ESP32`。
